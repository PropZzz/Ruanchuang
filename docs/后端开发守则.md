# 后端开发守则

**适用项目：** 时序智配（`Ruanchuang-main`）  
**当前基线：** FastAPI + SQLite + Flutter/Web 客户端  
**核心原则：** 先保证结果可信、可解释、可回滚，再追求语言和求解器性能。

## 1. 后端职责

后端负责四类工作：

1. 认证、用户隔离和权限校验。
2. 日程、任务、情绪/精力、事件和复盘数据的持久化。
3. 统一的日程规划、救援方案和问题诊断。
4. 为 Flutter 和 Web 提供稳定、可版本化的 REST 契约。

客户端负责交互、视图和离线缓存，不得各自维护一套生产排序规则。

## 2. 不可破坏的业务闭环

所有后端改动都必须服务于：

```text
突发任务输入
  -> 生成三种救援方案
  -> 比较代价和风险
  -> 用户确认
  -> 日程持久化
  -> 事件记录
  -> 可撤销
  -> 周/月复盘
```

禁止以下行为：

- 未经确认直接覆盖原计划。
- 保存失败后返回“成功”或生成虚假复盘记录。
- 把无可行时间块的计划返回为无风险计划。
- 把本地兜底数据标记为实时远端数据。
- 把预留接口、模拟数据或硬件能力描述为已实现。

## 3. 调度内核守则

### 3.1 模块边界

调度内核必须是无网络、无数据库副作用的纯计算模块：

```text
API Router
  -> Application Service
  -> SchedulerCore
       ├─ InputNormalizer
       ├─ ConstraintEngine
       ├─ TaskRanker
       ├─ PlacementScorer
       ├─ RescueStrategy
       └─ ExplanationBuilder
  -> Persistence Adapter
```

现有 `backend/services_scheduling.py` 可暂时作为兼容门面，但新逻辑应逐步收敛到独立的 `SchedulerCore`。

### 3.2 输入规范

任务至少包含：

```text
id, title, durationMinutes, priority, due, load, tag
```

允许逐步增加：

```text
hardDeadline, earliestStart, splittable,
minimumChunkMinutes, goalId, goalTaskId
```

新增字段必须可选、可向后兼容，并在服务端完成校验。时间统一使用明确的日期、时区和分钟精度。

### 3.3 约束优先级

候选时间块必须按以下顺序处理：

```text
1. 固定日程和不可占用区间
2. 工作时间窗
3. earliestStart
4. 硬截止时间
5. 任务依赖
6. 恢复缓冲
7. 软目标评分
```

无满足硬约束的候选时，可以返回最早可行结果，但必须记录：

```text
no_slot / miss_due / overdue / dependency_blocked
```

### 3.4 任务排序

```text
ASAP
  -> 硬截止可行性
  -> slack 剩余裕量
  -> 优先级
  -> 精力与认知负荷匹配
  -> 原计划稳定性
  -> 空档利用率
```

```text
slack = 截止时间 - 当前时间 - 剩余任务时长 - 恢复缓冲
```

同分时必须使用稳定的 `id` 作为最后排序键，保证 Python、Go、Rust 等实现返回一致顺序。

### 3.5 三种救援策略

三种策略必须共享同一个候选时间块计算器，只改变软目标权重：

```text
protectDeadline:
  urgency 0.55, priority 0.25, energyFit 0.10, stability 0.10

protectRecovery:
  energyFit 0.35, recovery 0.25, urgency 0.20,
  priority 0.10, stability 0.10

minimizeChanges:
  stability 0.55, urgency 0.25, priority 0.15, energyFit 0.05
```

恢复策略默认预留 15 分钟缓冲；策略不得绕过固定日程或硬截止校验。

### 3.6 解释结果

每个规划结果至少应包含：

```text
algorithmVersion
planId
entries[]
issues[]
movedEntryCount
recoveryMinutes
missedDeadlineCount
earliestFinish
scoreBreakdown[]
```

解释码必须稳定，例如：

```text
deadline_proximity
priority
energy_fit
kept_baseline
fixed_conflict
```

解释码是客户端文案映射的依据，不允许把无法计算的“AI 判断”写入结果。

## 4. API 守则

### 4.1 现有接口

不得无理由修改以下接口的字段含义：

```text
POST /auth/register
POST /auth/login
GET  /auth/me
GET/POST/PUT/DELETE /schedule
POST /schedule/replan
POST /events
POST /events/batch
GET  /energy/current
GET  /emotion/current
GET  /review/weekly
GET  /review/monthly
GET/PUT /review/tuning
```

新增字段优先采用可选字段，旧客户端必须仍能解析响应。

### 4.2 救援事务接口

第二阶段实现：

```text
POST /schedule/rescue/options
POST /schedule/rescue/apply
POST /schedule/rescue/undo
GET  /schedule/rescue/history
```

`apply` 必须携带：

```text
baselineHash
strategy
before
after
```

服务端必须验证基线未变化，并在一个事务中完成：

1. 更新日程。
2. 写入 `TaskEvent`。
3. 保存撤销快照。

任一步失败都要回滚，不得只更新部分日程。

## 5. 数据与并发

- 所有查询和写入都必须带当前用户过滤条件。
- 资源 ID 发生跨用户冲突时返回明确的冲突错误。
- 批量事件写入必须幂等，拒绝批内重复 ID。
- 日程应用和撤销必须支持基线哈希或版本号，防止 Web 覆盖 Flutter 的最新修改。
- SQLite 首版只允许单实例写入，建议开启 WAL 并持久化数据库目录。
- 多实例部署前必须完成持久化认证、并发控制和数据库迁移到 PostgreSQL 的评估。

## 6. 后端语言替换规则

### 6.1 推荐顺序

```text
Python FastAPI 规范实现
  -> Go 计算 Worker（性能确有瓶颈时）
  -> Rust/C++ 求解服务（复杂约束和大规模规划时）
```

语言替换只允许替换 `SchedulerCore Adapter`，不得同时重写认证、持久化和全部 API。

### 6.2 选择条件

保留 Python 的条件：

- 单用户或中小规模日程。
- 规划请求主要是几十到数百项任务。
- 主要目标是快速迭代规则、解释和比赛演示。

选择 Go 的条件：

- 规划请求并发明显增加。
- 需要低内存、快速启动和单二进制部署。
- 已有跨语言测试向量。

选择 Rust/C++ 的条件：

- 基准测试证明 Python 计算已经成为 P95 瓶颈。
- 需要依赖、任务拆分、容量和多目标约束联合求解。
- 已有稳定的超时、降级和解释方案。

Node.js/TypeScript 不作为 CPU 密集型求解核心；若使用，必须将规划计算放入 Worker Threads 或独立服务。

### 6.3 替换流程

1. 固化 JSON 请求/响应契约。
2. 固化跨语言测试向量。
3. 让新实现与 Python 返回相同的排序、问题码和解释码。
4. 通过配置切换：

   ```text
   SCHEDULER_ENGINE=python|go|rust|cpp
   ```

5. 先影子计算比较结果，再灰度切换，最后才移除旧实现。

## 7. 性能守则

首版使用可解释的启发式算法，基础复杂度允许为：

```text
O(n log n + n × m)
```

不要在没有基准数据时提前引入复杂求解器。优化顺序：

```text
1. 减少重复解析和重复构建固定区间
2. 复用三种策略的规范化输入
3. 使用稳定排序和区间索引
4. 必要时引入进程/Worker 计算
5. 最后才替换语言或约束求解器
```

性能验收必须使用真实规模的任务夹具，至少记录 P50、P95、P99、内存峰值、超时数和降级数。建议先设定“单日 200 项任务、三策略规划”的预算，再根据实测调整，不得把预算写成已达成指标。

## 8. 错误与降级

错误分类必须保持稳定：

```text
400/422  输入或校验错误
401      未登录或 Token 无效
403      无权限
404      资源不存在
409      基线或资源冲突
5xx      服务端故障
```

客户端只能在网络不可用或 5xx 时使用本地兜底。4xx、鉴权失败、冲突和响应格式错误必须原样暴露，不能转换为空列表或稳定默认值。

规划超时必须返回明确的超时状态，并保留原计划；不得在超时后悄悄写入部分结果。

## 9. 安全与部署

- 当前进程内 Token 只适合演示；正式多进程部署前改为签名 JWT、持久化会话或 Redis。
- 生产 CORS 不得使用 `*`，只允许正式 Web 域名。
- 数据库文件、密钥和用户数据不得提交到 Git。
- 生产环境使用 HTTPS，API 和静态 Web 文件可通过 Nginx 分流。
- 首版 SQLite 使用单 Uvicorn worker；扩容前先完成 PostgreSQL 和会话迁移。
- 每次发布前备份数据库，并保留回滚版本。

## 10. 测试守则

每次调度算法变更至少增加或更新：

- 固定日程不被覆盖测试。
- 截止时间可行性和 `miss_due` 测试。
- 低精力与高负荷任务匹配测试。
- 三策略结果和解释码测试。
- Dart/Python 跨语言一致性测试。
- 救援应用失败回滚测试。
- 救援撤销恢复基线测试。
- 用户隔离、重复 ID 和资源冲突测试。
- 超时和本地降级测试。

提交前运行：

```text
flutter analyze
flutter test -r compact
F:\Tools\Python310\python.exe -m pytest backend\tests -q
```

## 11. 开发决策记录

1. 先深化 Python 调度内核，不以“换语言”代替问题定位。
2. API 契约、测试向量和解释码是跨语言的稳定 Seam。
3. Web 与 Flutter 必须共享同一规划规则和数据事实。
4. 自动排程只生成建议；日程写入必须可确认、可回滚、可审计。
5. 所有性能结论以基准测试为准，不能使用语言宣传或理论峰值替代实测。
