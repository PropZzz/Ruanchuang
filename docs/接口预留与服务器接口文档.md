# 时序智配接口预留与服务器接口文档

日期：2026-08-09

## 文档目标

本文档用于指导后续在现有 `Ruanchuang-main` 项目中继续扩展服务器、远程接口、第三方集成、AI 能力和本地兜底能力。它同时记录当前已实现接口和未来必须预留的接口边界。

接口状态分为三类：

- `Implemented`：当前后端已有可调用路由或前端已有稳定服务入口。
- `Partial`：已有部分实现，但数据、页面、后端或测试尚未完全闭环。
- `Reserved`：为后续服务器、云服务、设备、第三方平台或 AI 服务预留，当前不得声称已完成。

## 当前服务器和客户端约定

当前后端为 FastAPI + SQLite。

默认开发服务器：

```text
http://127.0.0.1:8000
```

Android 模拟器访问本机后端：

```text
http://10.0.2.2:8000
```

Flutter 运行时可通过环境变量覆盖：

```powershell
flutter run --dart-define=API_BASE_URL=http://127.0.0.1:8000
```

生产环境预留：

```text
https://api.shixuzhipei.example.com
```

生产域名、证书、网关、负载均衡、对象存储和模型服务当前均为 `Reserved`，后续部署时再绑定真实配置。

## 通用协议

所有接口默认使用 JSON。

请求头：

```http
Content-Type: application/json
Authorization: Bearer <token>
```

未登录可访问：

- `GET /health`
- `POST /auth/register`
- `POST /auth/login`

其他接口默认需要 `Authorization`。

时间格式：

- 日期使用 `YYYY-MM-DD`。
- 月份使用 `YYYY-MM`。
- 时间点使用 ISO 8601 字符串。
- `TimeOfDay` 风格字段使用 `{ "hour": 9, "minute": 30 }`。

错误响应建议统一为：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "截止时间必须晚于当前时刻。",
    "details": {
      "field": "due"
    }
  }
}
```

通用错误码：

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | 请求格式错误 |
| 401 | `UNAUTHORIZED` | 未登录或 token 无效 |
| 403 | `FORBIDDEN` | 无权限 |
| 404 | `NOT_FOUND` | 资源不存在 |
| 409 | `CONFLICT` | 资源冲突、跨用户 ID 冲突、重复提交 |
| 422 | `VALIDATION_ERROR` | 字段校验失败 |
| 429 | `RATE_LIMITED` | 频率限制 |
| 500 | `INTERNAL_ERROR` | 服务端错误 |
| 503 | `SERVICE_UNAVAILABLE` | 服务器、模型服务或第三方服务暂不可用 |

客户端兜底规则：

- 只有网络不可达、超时、服务端 5xx 或 503 才允许回退本地。
- 400、401、403、404、409、422 不允许静默回退，应暴露给页面。
- 响应 JSON 格式错误不允许当成空数据。

## 日程救援接口

服务器端已实现完整救援事务：方案生成、原子采用、撤销快照与救援历史。Flutter 客户端当前仍使用本地救援闭环（`ScheduleRescueService` + `ScheduleRescuePersistence`），后续由成员 D 按远程优先、本地兜底策略接入。

| 方法 | 路径 | 状态 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/schedule/rescue/options` | Implemented | 输入紧急任务和当前日程，返回三种救援方案与基线哈希 |
| `POST` | `/schedule/rescue/apply` | Implemented | 验证基线后，在单个 SQLite 事务内原子写入日程、记录 `rescue_accept:<strategy>` 事件并保存撤销快照 |
| `POST` | `/schedule/rescue/undo` | Implemented | 使用确认前快照恢复日程并记录 `rescue_undo:<strategy>` 事件；失败保留当前方案，可重试 |
| `GET` | `/schedule/rescue/history` | Implemented | 查询救援接受和撤销历史，过滤与排序规则同 `/review/rescue-history` |

`POST /schedule/rescue/options` 请求：

```json
{
  "day": "2026-08-09",
  "urgentTask": {
    "id": "urgent_001",
    "title": "客户紧急问题",
    "durationMinutes": 60,
    "priority": 5,
    "load": "high",
    "tag": "Urgent",
    "due": "2026-08-09T15:30:00+08:00"
  },
  "currentEntries": [],
  "energy": "medium",
  "strategies": [
    "protectDeadline",
    "protectRecovery",
    "minimizeChanges"
  ],
  "windows": [
    { "start": { "hour": 8, "minute": 0 }, "end": { "hour": 18, "minute": 0 } }
  ]
}
```

`urgentTask.due` 必填（缺失返回 422）；`strategies` 非空、不重复且只能包含三种策略。`windows`、`tuning`、`fixed`、`tasks` 为可选增量字段，用于镜像客户端的调度请求（省略 `windows` 时引擎使用 8:00-20:00 默认窗口）。紧急任务"已过期"的判断由客户端完成，服务端只做结构性校验。

`POST /schedule/rescue/options` 响应：

```json
{
  "baselineHash": "64 位十六进制 SHA-256",
  "options": [
    {
      "id": "option_001",
      "strategy": "protectDeadline",
      "title": "优先保住截止时间",
      "recommended": true,
      "rationale": "先安排紧急事项，再重新分配其余任务，优先降低逾期风险。",
      "tradeoff": "可能移动更多原有任务，恢复时间取决于当前能量状态。",
      "movedEntryCount": 2,
      "recoveryMinutes": 0,
      "issueCount": 0,
      "affectedEntries": ["sch_001"],
      "plannedEntries": []
    }
  ]
}
```

- `recommended` 规则：问题数最少，其次移动任务数最少，再次按请求顺序最早。
- 三策略组合镜像客户端 `ScheduleRescueService`：`protectDeadline` 全量重排；`protectRecovery` 全量重排、能量降一档并加入 15 分钟恢复缓冲块；`minimizeChanges` 锁定当前日程、只把紧急任务放进空档。
- `baselineHash` 是当前日程条目的规范化哈希，`apply` 时必须原样回传。规范化规则：只纳入目标日的条目（`day=None` 的收件箱条目与其他日期条目除外）；每条目只取 `id/day/title/tag/load/goalId/goalTaskId/height/color/time/reminderMinutesBefore/repeat/repeatUntil` 十三个字段，`height` 保留两位小数吸收浮点噪声；按 `id` 升序排序后 `json.dumps(sort_keys=True)` 再取 SHA-256。客户端回传的 `currentEntries` 与数据库行经过同一函数后哈希一致。

`POST /schedule/rescue/apply` 请求：

```json
{
  "day": "2026-08-09",
  "baselineHash": "来自 options 响应",
  "strategy": "protectDeadline",
  "before": [],
  "after": [],
  "urgentTask": {},
  "eventId": "可选，客户端事件 ID，用于重试幂等",
  "energy": "medium"
}
```

`POST /schedule/rescue/apply` 必须满足：

- 服务端按当天数据库行重算哈希并与 `baselineHash` 比对，不一致返回 409 `CONFLICT`，不产生任何写入。
- 单个 SQLite 事务内完成：删除当天日程 → 写入 `after` → 写入 `rescue_accept:<strategy>` 事件（`type=interrupt`）→ 保存撤销快照；任一步失败全部回滚。
- 快照保存验证基线时读出的数据库行（不信任客户端的 `before`），返回快照 ID 作为撤销令牌。
- `after` 非空、条目 ID 非空且列表内唯一，否则 422。

`POST /schedule/rescue/apply` 响应：

```json
{
  "snapshotId": "快照 ID，用于撤销",
  "entries": [],
  "eventId": "救援接受事件 ID"
}
```

`POST /schedule/rescue/undo` 请求：

```json
{
  "snapshotId": "apply 返回的快照 ID",
  "eventId": "可选，客户端事件 ID"
}
```

`POST /schedule/rescue/undo` 必须满足：

- 使用确认前快照恢复当天日程。
- 记录 `rescue_undo:<strategy>` 事件（`type=interrupt`）。
- 撤销失败时保留当前方案并保持快照可重试；快照不存在或不属于当前用户返回 404，已撤销返回 409。

救援接口错误码遵循统一错误形状 `{"code", "message"}`：422 `VALIDATION_ERROR`（字段校验、非法策略）、409 `CONFLICT`（基线变更、跨用户 ID 冲突、重复撤销）、404 `NOT_FOUND`（快照不存在）。客户端不得把 409/404/422 静默回退到本地。

## 离线同步和冲突接口

离线同步是后续多端协同的关键预留能力，当前不得替代现有本地兜底逻辑。

| 方法 | 路径 | 状态 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/sync/pull?since=<cursor>` | Reserved | 拉取服务器增量变更 |
| `POST` | `/sync/push` | Reserved | 推送本地离线变更 |
| `GET` | `/sync/status` | Reserved | 当前同步状态 |
| `POST` | `/sync/conflicts/{conflict_id}/resolve` | Reserved | 用户确认冲突解决方案 |

冲突策略建议：

- 普通文本字段可使用最后写入优先，但必须保留审计。
- 日程时间冲突必须让用户确认。
- 日程救援采用和撤销必须保持顺序一致。
- 跨用户共享日程冲突不能静默覆盖。

## 前端服务层预留

新增接口时，Flutter 侧建议按以下层次接入：

```text
Screen / Widget
  -> AppServices
  -> DataService 抽象
  -> CompositeDataService
  -> RemoteDataService / LocalDataService
  -> ApiClient / LocalPersistence
```

建议新增服务边界：

- `AuthService`：生产级 token、刷新、退出登录。
- `ScheduleRescueService`：三方案、确认、撤销、事件记录。
- `SyncService`：离线变更队列、冲突处理。
- `IntegrationService`：第三方平台授权和导入。
- `AiGatewayService`：任务解析、目标拆解、方案解释。
- `DeviceDataService`：蓝牙、穿戴、采样数据。
- `NotificationService`：本地提醒和远程推送统一门面。

要求：页面层只依赖服务抽象，不直接拼接 URL。

## 实施优先级

第一优先级：

- 稳定日程救援闭环。
- 稳定事件批量写入。
- 稳定远程优先、本地兜底。
- 稳定复盘救援记录。

第二优先级：

- 目标、情绪、团队协作的服务器接口。
- 离线同步和冲突处理。
- 提醒与设备注册。

第三优先级：

- 第三方办公软件和日历集成。
- AI 能力网关。
- 生产服务器、对象存储、模型服务和多端实时同步。

## 开发注意事项

预留接口时可以写文档、抽象类、路由占位规划和测试期望，但不要让未实现接口在 UI 中表现为已可用。

新增接口必须保持前后端字段命名兼容，优先使用现有 Flutter model 的 JSON 字段。

涉及日程写入的接口必须考虑撤销和事件记录。

涉及跨端或团队数据的接口必须考虑权限和冲突。

涉及 AI、设备、第三方平台的接口必须有用户确认步骤，不能直接改写日程。
