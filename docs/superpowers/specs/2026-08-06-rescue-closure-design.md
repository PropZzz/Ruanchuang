# 日程救援闭环设计

**状态：** 已确认，待实现

## 目标

将“突发任务 - 方案比较 - 用户确认 - 可撤销执行 - 决策复盘”做成可在真实日程中持续使用的闭环：用户输入实际截止时刻；确认结果在重启后仍保留；用户能在复盘页查看每次救援的策略选择与撤销记录。

## 范围与边界

- 保留现有三种策略、启发式调度引擎、`DataService`、远程 REST API 及 SQLite `TaskEvent` 表。
- 不增加后端表、不接入第三方日历，也不改变非救援场景的普通日程编辑流程。
- 救援同步只处理本次方案前后拥有稳定 ID 的日程条目。未出现在当前智能计划中的用户日程不删除。

## 交互设计

### 紧急任务

智能日历的“插入紧急任务”弹窗增加“截止时间”行。默认值为：当天选取当前时刻两小时后；未来日期默认 17:00。用户通过系统时间选择器修改时刻。

提交前校验：选中日期不得早于今天；若是今天，截止时刻必须晚于当前时刻。校验失败时保持弹窗打开并显示本地化提示。成功后以选中日期和时刻组成 `PlanTask.due`，再显示原有三张救援方案卡片。

### 确认与撤销

确认方案时，页面先将方案日程同步到 `DataService`，成功后才更新可见日历、启用撤销横幅、重排提醒并记录 `rescue_accept:<strategy>` 事件。写入失败时，页面保留原计划并显示现有错误反馈。

撤销时执行反向同步：移除仅存在于接受方案中的条目，恢复确认前条目；同步成功后才恢复页面状态并记录 `rescue_undo:<strategy>`。任一同步步骤失败时，持久化辅助服务以确认前的快照进行补偿恢复，并将错误抛给页面处理。

### 复盘

复盘页按当前周或月读取 `TaskEvent`，筛选 `reason` 为 `rescue_accept:` 或 `rescue_undo:` 的事件，在统计内容后显示“日程救援记录”。每条记录显示时间、任务标题、策略名称和“已采用”或“已撤销”状态；无记录时显示空状态。策略名称由已有枚举名称映射到中英文文案。

## 组件与数据流

新增 `ScheduleRescuePersistence`，依赖 `DataService`：

1. `apply(before, after)` 计算两组稳定 ID 的差集。
2. 对 `after` 中的条目调用 `addScheduleEntry`，以原有 upsert 语义新增或更新。
3. 对只存在于 `before` 的条目调用 `removeScheduleEntry`。
4. 若步骤 2 或 3 失败，执行补偿：恢复 `before`，再清理仅在 `after` 中的条目，随后抛出原始错误。

页面继续保存确认前的 `_rescueUndoBlocks`，它既是撤销快照，也是传给持久化服务的 `before` 集合。现有 `CompositeDataService` 会先尝试远端再写入本地，因此离线时仍能保存本次救援。

```text
输入截止时刻 -> 生成三方案 -> 用户选择
    -> 持久化方案 -> 更新界面与提醒 -> 记录接受事件
    -> 撤销时反向持久化 -> 更新界面 -> 记录撤销事件
    -> 个人中心 / 复盘页查看救援记录
```

## 错误处理

- 截止时间非法：不生成方案，不修改日程。
- 持久化失败：不更新内存状态、不重排提醒，显示“暂时无法保存救援方案”。
- 事件记录失败：沿用本地优先 `CompositeDataService`；若最终仍失败，不回滚已成功保存的日程，但记录诊断并保持救援可见。
- 撤销持久化失败：保持已采用方案和撤销横幅，便于用户重试。

## 测试策略

- 为 `ScheduleRescuePersistence` 编写测试：接受方案新增/更新条目，撤销恢复原条目，写入失败时补偿回原状态。
- 扩展智能日历组件测试：截止时间可选且非法值被拒绝；插入紧急任务后可以看到三方案并确认。
- 扩展复盘页组件测试：接受和撤销事件显示正确的任务、策略与状态。
- 运行 `flutter analyze`、全部 Flutter 测试和 `backend/tests`；后端测试预期无需代码变更。
