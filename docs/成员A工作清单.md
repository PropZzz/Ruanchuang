# 成员 A 工作清单

> 依据：`docs/五人开发分工文档.md`，成员 A 的岗位是“项目负责人 / 架构与调度内核”。

## 一、岗位目标与边界

成员 A 的核心目标是保证产品主线、数据契约和调度/救援规则只有一个可信来源。

负责范围：

- `docs/` 中的架构、接口、后端守则和决策记录。
- `backend/services_scheduling.py`，以及后续独立的 `SchedulerCore`、测试向量和基准脚本。
- `lib/services/scheduling/` 中的 Dart 调度接口、策略和本地救援规则。

不负责页面视觉重做、数据库迁移实现、生产服务器运维和硬件接入。

## 二、执行步骤

### 1. 冻结当前项目基线（P0）

这是成员 A 当前最先执行的工作。

1. 盘点 `main` 相对远端领先的 13 个提交。
2. 盘点全部未提交、新增和删除文件。
3. 按以下类别整理变更：
   - 前端视觉
   - 后端行为
   - 删除文件
   - 资源文件
   - 文档
4. 为每个文件标注责任人、保留/删除结论和风险。
5. 汇总成员 B、C、D、E 的复核结果。
6. 将已确认的改动拆成多个可回滚的小提交。
7. 建立可复现的基线提交或标签。

交付物：

- 当前变更清单
- 提交拆分方案
- 文件责任人和去留结论
- 基线提交或标签

完成标准：所有未提交文件都有责任人和处理结论，团队可以从固定基线复现当前状态。

### 2. 锁定调度数据契约

成员 A 需要定义调度系统统一的输入和输出格式，避免 Dart、Python 和 API 各自解释字段。

需要明确：

- 任务字段：`id`、`title`、`durationMinutes`、`priority`、`due`、`load`、`tag` 等。
- 可选字段：`hardDeadline`、`earliestStart`、`splittable`、`minimumChunkMinutes`、目标关联字段。
- 日期格式：`YYYY-MM-DD`。
- 时间格式：ISO 8601，并明确时区和分钟精度。
- 相同优先级、相同截止时间下的稳定排序规则。
- 调度输出中的任务顺序、时间块、风险和解释字段。
- 问题码：`no_slot`、`miss_due`、`overdue`、`dependency_blocked`。

交付物：

- 调度输入 JSON 契约
- 调度输出 JSON 契约
- 字段兼容性说明
- 问题码和解释码说明

### 3. 明确三种救援策略

为每种救援策略写清楚：

- 适用场景
- 固定日程是否允许移动
- 截止时间如何处理
- 低精力任务如何匹配
- 任务移动数量如何计算
- 恢复缓冲如何计算
- 逾期风险如何计算
- 各项约束、权重和优先级
- 最终解释码如何生成

调度必须先满足固定日程、工作窗口、截止时间和依赖，再进行软评分，不能为了提高评分破坏硬约束。

### 4. 与成员 B 锁定远端救援事务契约

成员 A 负责业务规则和接口语义，成员 B 负责 FastAPI、数据库和事务实现。

需要共同定义：

- `/schedule/rescue/options`
- `/schedule/rescue/apply`
- `/schedule/rescue/undo`
- `/schedule/rescue/history`
- `baselineHash` 的生成和校验方式
- 版本冲突的返回语义
- 方案采用前是否只返回草案
- 采用方案时如何写入日程和事件
- 撤销时如何恢复原始快照
- 保存失败时如何完整回滚
- 远端能力未完成前继续保持 `501`

完成标准：任一步保存失败，都不能留下部分日程、虚假事件或错误的成功提示。

### 5. 将调度逻辑收敛为纯计算的 `SchedulerCore`

调度链路应保持为：

```text
API Router
  -> Application Service
  -> SchedulerCore
  -> Persistence Adapter
```

`SchedulerCore` 内部可以拆为：

- `InputNormalizer`
- `ConstraintEngine`
- `TaskRanker`
- `PlacementScorer`
- `RescueStrategy`
- `ExplanationBuilder`

必须保证：

- 不访问网络。
- 不访问数据库。
- 不执行持久化。
- 不直接处理事务。
- 原有 `services_scheduling.py` 可以暂时作为兼容门面。

### 6. 建立 Dart/Python 共享测试向量

至少覆盖以下场景：

- 固定日程冲突
- 工作窗口限制
- 截止时间不可行
- 依赖阻塞
- 低精力任务匹配
- 三种救援策略
- 无可用时间块
- 逾期任务
- 应用失败回滚
- 撤销后恢复原计划
- 超时和边界时间

执行流程：

1. 准备共享 JSON fixtures。
2. 分别运行 Dart 和 Python 实现。
3. 对比任务顺序、时间块、问题码和解释码。
4. 输出差异报告。
5. 判断差异属于实现错误、契约错误还是允许的差异。
6. 在双方对齐前，不单独修改某一端并宣称结果一致。

### 7. 补充基准和性能证据

在规则正确、跨语言结果一致后，建立调度基准脚本，记录：

- 任务数量
- 规划耗时
- 超时行为
- 不同策略的结果
- 失败和降级情况

没有基准数据前，不推动 Go、Rust 或 C++ 重写调度核心。

### 8. 维护技术决策、风险和合并审查

每个阶段维护：

- 技术决策记录
- 当前风险清单
- 契约变更记录
- 跨模块影响说明
- 回滚方案
- 合并审查结论

任何新增字段、接口或状态，都要同步检查模型、服务层、页面状态、测试和文档，不能只修改一端。

### 9. 负责阶段门禁和项目节奏

成员 A 的协作职责：

- 周初更新优先级和接口变更。
- 开发中审查跨边界修改的影响和回滚方式。
- 周末确认核心业务是否满足阶段门槛。
- 发布前确认“当前任务 -> 调度 -> 救援比较 -> 采用 -> 撤销”的业务闭环。

在 P1 调度与救援正确性完成前，不启动 AI、设备、第三方日历、离线同步等 P4 工作。

## 三、阶段交付物汇总

| 阶段 | 成员 A 的主要交付物 | 完成判断 |
| --- | --- | --- |
| P0 基线冻结 | 变更清单、提交拆分方案、责任人结论、基线标签 | 所有改动可追踪、可回滚、可复现 |
| P1 契约设计 | 调度 JSON 契约、问题码、解释码、三策略规则 | Dart、Python、API 对字段和语义一致 |
| P1 内核实现 | `SchedulerCore`、共享测试向量、差异报告、基准脚本 | 调度无外部副作用，跨语言结果一致 |
| P1 救援事务 | 远端救援契约、冲突规则、回滚和撤销规则 | 失败不会产生部分写入或虚假事件 |
| 持续治理 | 决策记录、风险清单、合并审查结论 | 每次跨边界变更都有影响和回滚说明 |

## 四、必须避免的越界行为

- 不在调度模块中访问网络或数据库。
- 不为了通过测试偷偷改变截止时间、固定日程或回滚语义。
- 不在没有基准数据时推动更换调度语言。
- 不把页面视觉、数据库迁移、生产运维或硬件接入纳入自己的实现范围。
- 不在 P1 未完成时启动 AI、设备、第三方集成或多端同步。

## 五、最终完成标准

成员 A 的工作完成，至少应满足：

1. 项目基线清晰、变更责任明确、可以回滚。
2. 调度输入、输出、排序、问题码和解释码已经统一。
3. 三种救援策略有明确的约束和权重说明。
4. `SchedulerCore` 是无网络、无数据库副作用的纯计算模块。
5. Dart/Python 共享测试向量通过，差异有记录并已处理。
6. 本地救援闭环和远端救援事务都有可重复测试。
7. 失败时不会留下部分日程、虚假事件或错误成功提示。
8. 每个阶段都有技术决策、风险和合并审查记录。
