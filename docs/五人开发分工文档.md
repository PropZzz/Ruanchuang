## 1. 文档目的

本文用于统一回答四个问题：

1. 当前项目已经做到什么程度。
2. 下一阶段先做什么、后做什么。
3. 哪些模块由谁负责，哪些地方不能越界修改。
4. 以什么证据判断一个阶段真正完成。

本文只基于当前 `Ruanchuang-main` 工作树、代码、测试和现有设计/接口文档判断，不把设计稿、预留接口、模拟数据或本地预览当成生产能力。

## 3. 下一阶段工作顺序

### P0：冻结并整理当前基线

**目标：** 让五人团队知道哪些改动已经完成、哪些改动仍在工作树中，避免在未审查的混合状态上继续叠加功能。

- 成员 A 建立当前变更清单，按“前端视觉、后端行为、删除文件、资源、文档”分类。
- 成员 B 逐项复核后端未提交改动，确认数据库初始化、Schema、路由和调度逻辑没有误删行为。
- 成员 C/D 复核 Flutter 未提交改动，确认页面业务逻辑、远端/本地服务和模型字段未被视觉改动破坏。
- 成员 E 重新跑三组基线验证，保存输出和版本信息。
- 通过审查的改动拆成可回滚提交；未确认的改动不得混入下一功能分支。

**完成门槛：** 有一份变更清单、一个可复现的基线提交/标签、所有未提交文件都有责任人和去留结论。

### P1：先稳定核心调度与救援正确性

1. 将 `backend/services_scheduling.py` 逐步收敛为纯计算的 `SchedulerCore`，路由、事务和持久化不进入算法模块。
2. 固化任务字段、时间格式、稳定 ID 排序、`no_slot`/`miss_due`/`overdue`/`dependency_blocked` 等问题码。
3. 建立 Dart/Python 共享 JSON 测试向量，先保证排序、约束和解释码一致，再考虑换语言。
4. 设计并实现远端救援事务：基线哈希、方案采用、事件写入、撤销快照、失败回滚；完成前保持 501 边界。
5. 补充固定日程、截止可行性、低精力匹配、三策略、应用失败回滚、撤销恢复基线和超时测试。

**完成门槛：** 本地救援闭环和远端事务都有可重复测试；任一步保存失败都不会留下部分日程或虚假事件。

### P2：补齐前端状态与交互验收

- 为 Focus、智能日历、微任务、团队、目标、复盘和登录页面补齐统一状态映射。

- 继续拆分超大页面，但只做有明确边界的组合组件；组件不能直接访问网络、数据库或全局单例。

**完成门槛：** 五个尺寸无阻断性布局问题，关键错误有可见原因和下一步操作，关键流程不依赖 hover 或拖拽。

### P3：生产化准备与发布证据

- 明确首版继续使用 SQLite 单 Uvicorn worker，还是进入 PostgreSQL 迁移；没有迁移和并发证据前不扩容。

**主责目标：** 保证产品主线、数据契约和调度/救援规则只有一个可信来源。

**负责目录与文件：**

- `docs/` 中的架构、接口、后端守则和决策记录。

- `lib/services/scheduling/` 中 Dart 调度接口、策略和本地救援规则。

**必须交付：**

### 5.1 不可随意拆分的公共边界

客户端和后端必须遵循以下链路：

```text
Screen / Widget
  -> AppServices
  -> DataService
  -> CompositeDataService
  -> RemoteDataService / LocalDataService
  -> ApiClient / LocalPersistence
```

调度必须遵循以下链路：

```text
API Router
  -> Application Service
  -> SchedulerCore（纯计算）
  -> Persistence Adapter
```

任何人新增接口、字段或状态时，都必须同时更新模型、服务层、页面状态、测试和对应文档；不能只改一端。

## 6. 统一开发规则

### 6.1 数据和错误语义

- 日期统一 `YYYY-MM-DD`，时间点使用 ISO 8601，`height` 与时长保持现有兼容换算（`80.0` 约等于 60 分钟）。
- 调度先满足固定日程、工作窗口、截止时间和依赖，再做软评分。
- 事件批量写入必须拒绝空 ID、批内重复 ID 和跨用户冲突，并具备幂等性。
- 远端成功、本地模式、待同步、无数据、冲突、预留和超时必须是不同状态。
- 任何错误都要告诉用户“发生了什么”和“下一步能做什么”；不得把失败静默成空列表。

### 6.2 Reserved 边界

以下能力在未完成契约、权限、失败、回滚和测试前保持 Reserved/501：

- 日程救援远端事务、ICS 导入导出、批量日程和冲突接口。
- 离线同步、冲突解决、跨端实时协作。
- 生产级 token 刷新/退出、PostgreSQL、多实例部署和正式 CORS。
- 团队冲突检测、黄金窗口、预约会议。
- 设备、蓝牙采样、推送、第三方日历、文件/对象存储和 AI 网关。

允许写文档、抽象接口、占位测试和 501 路由；不允许在 UI 中伪装成可操作成功。

### 6.3 Git 与合并

- P0 完成前，不在当前混合工作树上继续大规模重构。
- 每个成员使用短分支和小提交；公共文件冲突优先由主责人合并。
- 提交信息说明行为变化；格式化、资源替换和业务修改不要混成一个不可审查提交。
- E 的验收不通过时可以阻止合并；不能通过删除测试或放宽断言解决。
- 合并前保留完整工作树状态、测试输出和已知缺口；不能声称已同步 GitHub 或已部署生产，除非有对应证据。

| 后端验收 | API 成功/鉴权/校验/冲突/事务/隔离测试通过 | 只有 `/health` 200 |

| 生产/现场 | 真实域名、真实设备/网络、外部服务、性能和运维证据 | 设计文档、预留路由、单元测试 |

## 8. 每周协作节奏

1. 周初：A 更新优先级和接口变更；B/D 确认依赖；C 确认页面验收项；E 建立本周证据清单。
2. 开发中：每项任务只保留一个主责人；跨边界修改先在 PR 描述中写清影响和回滚方式。
3. 周中：E 跑一次增量回归，提前暴露契约、布局和环境问题。
4. 周末：全员按阶段门槛验收；未完成项写入“缺口/下一步”，不改成完成。
5. 发布前：由 E 给出“可发布/阻塞”结论，由 A 确认业务闭环，由 B 确认数据和服务安全，由 C/D 确认客户端状态诚实。
