## 项目背景

项目名称为“时序智配 / Temporal Intelligence Scheduler”，是一个面向高压知识工作者的认知适配型智能日程调度平台。它的核心不是普通日历，而是在突发任务、会议延期或精力下降打乱原计划时，生成可解释的重排方案，让用户在截止时间、恢复时间和计划稳定性之间做选择，并把选择结果进入复盘闭环。

当前项目重点验证这条主线：

```text
突发任务 -> 三方案比较 -> 用户确认 -> 可撤销执行 -> 事件记录 -> 周/月复盘
```

任何优化都必须服务这条主线，不能为了新增功能牺牲用户确认、撤销、持久化和复盘可追踪性。

## 技术栈和边界

前端保持 Flutter/Dart + Material 3，不迁移到 React、Vue、小程序或其他框架。

后端保持 FastAPI + SQLite，不迁移到 Node.js。后续可以预留 PostgreSQL、云服务器、对象存储、模型服务和第三方集成接口，但当前实现不得假装这些能力已经真实落地。

状态管理沿用现有 `StatefulWidget`、`setState`、`DataService`、`AppServices`、`CompositeDataService` 模式，不引入 Riverpod、Provider、GetX 等大型状态管理方案。

数据访问必须通过服务层完成。页面不要直接硬编码 HTTP 请求、数据库访问或本地存储读写。

## 现有架构要点

前端主要目录：

- `lib/models/models.dart`：核心模型，包括 `ScheduleEntry`、`MicroTask`、`TaskEvent`、`Goal`、`TeamMemberCalendar`、`ReviewReport` 等。
- `lib/services/`：服务层，包含本地、远程、组合数据服务以及提醒、排程、复盘等服务。
- `lib/screens/`：页面层，包括专注、智能日程、微任务、团队、我的、复盘等。
- `lib/widgets/`：可复用组件。
- `lib/config/app_config.dart`：API 地址配置，支持 `--dart-define=API_BASE_URL=...`。
- `test/`：Flutter 单元测试和组件测试。

后端主要目录：

- `backend/main.py`：FastAPI 应用入口。
- `backend/routers_*.py`：认证、日程、微任务、事件等路由。
- `backend/schemas.py`：Pydantic 请求和响应模型。
- `backend/repositories.py`：SQLite 数据访问。
- `backend/services_scheduling.py`：排程算法服务。
- `backend/services_microtask.py`：微任务晶体推荐服务。
- `backend/tests/`：后端测试。

## 核心业务规则

紧急任务必须填写精确截止日期和时间。缺失、格式无效或已经过期的截止点不能提交。

系统一次给出三种可解释的救援策略：

- 优先保住截止时间：优先安排紧急事项，允许移动更多普通任务。
- 优先保留恢复时间：降低高负荷安排倾向，并预留恢复缓冲。
- 尽量少动原计划：锁定已有日程，优先使用现有空档。

三种方案必须展示理由、代价、移动任务数量、恢复缓冲、受影响任务和问题数量。推荐方案可以突出，但不得自动采用。

用户确认后才写入日程。确认成功后要支持撤销，撤销应恢复确认前快照。

确认和撤销都要写入 `TaskEvent`，`reason` 使用稳定前缀，例如 `rescue_accept:<strategy>`、`rescue_undo:<strategy>`，用于复盘页筛选展示。

模拟周数据或批量事件写入必须保持原子性。写入失败时不得留下部分事件，也不得生成误导性的复盘报告。

## 数据服务和远程兜底规则

客户端采用远程优先、本地兜底：

- 后端可用时优先读写 REST API。
- 后端不可用、网络超时或服务端 5xx 时才允许落到本地。
- 4xx、认证失败、校验失败、冲突、响应格式错误必须暴露给调用方，不能吞掉后返回空数据。
- 远端写入成功后，本地缓存同步是尽力而为，缓存失败不能诱导用户重复提交。

新增或优化接口时，优先遵守 `docs/接口预留与服务器接口文档.md` 中的路径、字段、错误码和预留状态。

## 接口预留要求

如果本次优化涉及未来功能但暂不实现完整后端，请只做清晰的接口预留，不要伪造真实能力。

接口预留应包含：

- 前端服务抽象方法或后端路由规划。
- 请求和响应字段。
- 鉴权要求。
- 错误码。
- 与本地兜底的关系。
- 测试或文档说明。

以下方向必须预留可扩展接口：

- 生产服务器地址与环境配置。
- 用户认证、刷新令牌、退出登录和用户资料。
- 日程 CRUD、智能重排、日程救援确认和撤销。
- 批量事件写入、周/月复盘、救援记录。
- 微任务 CRUD、批量处理、碎片时间推荐。
- 情绪和能量状态。
- 目标拆解、目标任务依赖、下一任务安排。
- 团队成员、共享权限、黄金协作窗口、会议预约。
- 提醒、通知、设备注册、蓝牙和穿戴设备。
- 第三方办公软件、日历、邮件、文档、出行和学习平台集成。
- AI 能力网关，例如任务解析、目标拆解、方案解释和调参建议。
- 离线同步、冲突解决和增量拉取。

## UI 优化标准

界面要像一个冷静、可信、可快速扫描的调度工作台，而不是营销页。

遵守现有 UI 重构标准：

- 使用 Material 3。
- 使用 6px 或 8px 圆角。
- 使用 8px 间距基线。
- 使用低对比边框、轻量表面和清晰层级。
- 不使用渐变、毛玻璃、装饰性光晕或过度卡片堆叠。
- 所有状态同时依赖文字、图标或标签，不只靠颜色。
- 桌面端优先服务规划、比较、复盘和团队协作。
- 移动端优先服务快速捕获、执行、确认和撤销。

必须保证 1440px 桌面宽度和 390px 移动宽度下，五个主模块可达，关键文字和按钮不重叠、不溢出、不遮挡。

## 编码要求

异步操作后调用 `setState` 前必须检查 `mounted`。

`Timer`、流、订阅、控制器等资源必须在 `dispose()` 中清理。

新增展示组件应尽量做成纯展示组件，通过参数接收数据和回调，不要直接依赖 `AppServices`。

新增模型字段要保持前后端 JSON 命名一致。Flutter 端常用 camelCase，例如 `goalId`、`durationMinutes`、`reminderMinutesBefore`、`plannedMinutes`。

中文用户可见文案优先集中到 `lib/utils/app_strings.dart`，避免页面里散落硬编码。

不要删除本地兜底功能。后端未实现的功能仍应能通过本地服务维持基础体验。
